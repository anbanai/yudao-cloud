# 易宝多商家支付独立审查记录

审查基线：`54cead8d6`；目标分支：`teaworthshare`。审查范围覆盖支付、商家入网、交易改价、按商家售后退款、资金补偿、回调、账单对账及管理入口。最终隔离工作区的全量构建和逐文件差异复核由集成任务执行，本记录列出已完成的独立验证及其边界。

## 官方协议依据

- [官方 Java SDK 指南](https://open.yeepay.com/docs/open/platform-doc/sdk_guide-sm/java-sdk-guide-sm)：使用 `com.yeepay.yop.sdk` 官方客户端、数字信封和回调引擎；没有自行实现易宝请求签名或回调验签。
- [商户对账说明](https://open.yeepay.com/docs/products/ptssfk/others/5f9a6ea1f8301e001b1a870f)：交易与分账日账单通过官方 YOS 下载接口取得，平台商编作用域，次日 09:00 后获取。清算由原交易查询的 `clearStatus` 核对。
- [手续费补贴契约](https://open.yeepay.com/apis/docs/products/ptssfk/20260923120830/others/5f3cef4420289f001ba82523/656ed87c9a76e60072dd728b.html)：活动号通过 `feeSubsidyInfo` 官方数组格式传递。平台承担/全额补贴未确认时拒绝新支付。

## 计划与审查证据

| 计划要求 | 实现及验证重点 |
| --- | --- |
| 一个整单固定平台收款、最多五个商家 | 不可变资金主单/商家明细；合计整数分校验；平台收款快照；配置上限不得突破首期五商家硬限制 |
| 官方 SDK、统一平台微信 AppID | 官方 YOP/YOS 请求及回调引擎；RSA/SM2 协议测试；微信参数标准化；AppKey、私钥、公钥和证书正文仅运行时注入，持久化配置保存引用 |
| 只有完成入网的商家参与收款 | 入网数据库事务/隐私测试；后台提交及查询；补件重提稳定请求号；审批与出站请求解耦 |
| 预支付前冻结快照、稳定幂等 | 同一支付单并发锁定原外部单号；资金快照提交后才出网；商编配置变化不修改原资金主体 |
| 改价后资金计划一致 | 金额和明细单事务更新，禁止只有金额变化而残留旧计划；冻结后拒绝改价 |
| 支付与清算/分账解耦 | 首期强制 `DELAY_SETTLE`，拒绝实时分账配置；只由明确 `clearStatus=SUCCESS` 触发分账；支付 `status=SUCCESS` 不代表清算成功；并发查询租约仅一个有效请求 |
| 异步分账、幂等和人工补偿 | 固定分账号，PROCESSING 查询，退避及重试耗尽转人工；人工操作记录原因/操作者/凭证，外部请求在审计事务之外 |
| 按商家售后部分退款 | 原资金明细分配与累计上限校验；已分账先资金归还再退款；未分账只用退款内归还明细；实际归还成功或结果不明时，退款失败不能释放商家额度；人工恢复已提交终态退款只查询原请求号 |
| 快速 ACK、完整事件原文归档 | 验签后同步持久化事件及 AES256-GCM 加密原文；随机 nonce、租户/渠道/事件 AAD、轮换密钥编号；线程池拒绝后由持久事件补偿 |
| 回调租户和渠道隔离 | 所有六类回调绑定原渠道租户；外部事件号按可信渠道去重；旧统一入口也走归档/验证路径；授权及 Cookie 不归档 |
| 原资金身份校验 | 支付/清算/退款查询及回调核对原父商编、收款商编、订单号、易宝单号及整数分金额，禁止用最新配置覆盖历史快照 |
| 每日双向对账 | 原平台作用域、历史关闭渠道、UTF-8/CSV/固定表头/严格日期/汇总校验；成功本地流水缺失、外部孤儿、金额/状态/商编/明细号差异均落库 |
| 差异不可静默忽略 | 重跑保留未解决差异；新证据生成新差异；下载/格式错误进入人工状态；人工关闭要求理由和外部凭证 |
| 默认关闭灰度及历史任务继续 | 新订单使用渠道启用校验；历史查询/退款/补偿允许已关闭渠道；手续费保障默认未确认 |

## 已有真实 RED 的修复

审查过程中先运行失败用例，再修复以下问题；没有把失败测试简单改为忽略。

1. 支付成功被误当作清算成功，导致过早分账；改为只读取明确清算状态。
2. 清算并发扫描重复出网并消耗重试额度；增加可恢复租约与状态条件更新。
3. 异步事件线程池饱和使已持久化回调无法 ACK；捕获拒绝并保留待补偿事件。
4. 累计退款整数溢出绕过原订单金额上限；比较改为 `long`。
5. 人工重试可能把已成功资金记录降回 PROCESSING，且在审计事务内查询渠道；改为锁内准备、提交后执行、条件更新。
6. 老统一支付/退款回调入口绕过资金校验与事件归档；委托专用入口并保留官方 ACK 头和正文。
7. 缺失原资金快照时仍可能开始资金归还；退款准备前先验证原快照。
8. 商家入网回调只有 `requestNo` 时无法建立事件键；纳入申请号和申请进展字段。
9. 同租户不同渠道使用相同渠道级事件号时被误判重复；去重键加入服务端可信渠道号。
10. 账单日期被宽松解析器自动纠正，以及最小 `long` 退款金额无法转为正整数分；使用严格日历解析并校验正数归一结果。
11. 原回调仅有摘要哈希，缺少计划要求的加密原文；新增独立外部归档密钥和同事务密文存储，禁止普通 JSON/日志输出。
12. 已归还商家资金但用户退款失败时，整体失败状态释放原商家额度，后续退款可再次归还并超额；累计校验改为同时保留已成功或结果不明的实际归还额度，未分账的“无需归还”标记不误当资金已归还。
13. 已提交的终态失败退款无法进入人工查询恢复；人工操作保留原提交时间、请求号及归还证据，只恢复原请求查询资格，缺少提交凭证时转人工且禁止重新提交。
14. 归还回调先读取旧退款状态，可能覆盖并发提交的退款人工状态；使用数据库当前退款状态的条件更新。相反方向的旧退款失败行也可能覆盖刚完成的归还状态，失败更新同样基于数据库当前归还证据计算人工状态，不增加跨表锁序。
15. 迟到归还结果把已成功退款时间写成旧行中的 NULL；归还更新不写退款成功时间，保留两个独立的完成时间。
16. 商家详情、上传和补料响应在切换商家或关闭抽屉后仍能回写；增加请求上下文校验，上传绑定原任务和字段，提交后只刷新当前上下文。
17. 商家分页或筛选请求乱序时，旧响应覆盖新页数据、总数、错误和加载状态；独立列表请求序号保护全部回写，卸载时使在途响应失效。

配置审查另补充以下收口：平台父商编必填，首期拒绝 `REAL_TIME_DIVIDE`，删除预支付实时分账分支，外部凭证正文不进入渠道 JSON；显式引用通过运行时环境或 JVM 属性解析，签名契约测试验证引用确实进入官方 SDK。全量支付测试发现 Lombok 默认配置相等性会调用密钥 getter；改为直接比较配置字段，新增空配置、缺失引用及同值不同引用的相等性/哈希回归，保留真实使用凭证时的失败校验。

## 隔离集成与数据库范围

集成使用从基线建立的工作区，易宝提交保留基线审批入口及其同事务入网触发，未混入并行开发中的新版商家申请流程。共享工作区恢复新版申请功能时保留 `approveByApplication`，入网触发位于 `ProductMerchantApplicationServiceImpl.approve()` 的完整审批事务末端；不恢复已被新版移除的入口，也不重复触发入网。共享适配用例已单独执行并通过，见上述 24 用例日志。

已逐字段比较 9 个支付资金 DO 与八种数据库建表脚本，另核对 2 个商品入网任务 DO 的字段、Oracle 序列、SQL Server 可空唯一约束，以及旧表升级和加密迁移边界。PostgreSQL 家族脚本的语法解析及静态审查不能代替八种真实数据库执行。已有试验资金表须逐列核对专项 ALTER，不能将首次建表脚本当作自动升级。

基线缺失的 Brand/SPU 方法合同作最小补全；新增可用商品查询已改为参数绑定商家状态和删除标记，避免硬编码 `FALSE` 在 Oracle/SQL Server 等数据库不兼容。两项回归验证冻结、删除、缺失商家不可命中，以及空 ID 集合不触发全量查询。

最终隔离支付全量、商品/交易全量、聚合服务打包、管理前端、小程序及共享新版审批兼容已取得并读取上述成功日志。2026-10-11 本轮静态 `git diff --check 54cead8d6` 通过，退款 Mapper、配置及客户端测试共享/隔离 SHA256 一致。代码范围未发现剩余阻断问题，可进入本地 `teaworthshare` 合并；合并操作由集成任务执行，并逐文件核对共享工作区残留改动。

合并保留脚本审查补齐了以下保护：来源工作区必须全部提交且干净；目标分支/基线、索引、路径集合和文件摘要必须未变；备份所有任务及原脏路径；拒绝未处理的删除、目录及符号链接；仅在任务路径暂复基线，并按不可变目标 SHA 快进；异常可从原内容备份恢复。共享现有文件优先保留会产生整文件残留候选，必须继续核对候选包含易宝修改与并行开发修改，不能仅凭脚本摘要一致就认定语义合并正确。

## 发布前置条件

代码合并不等于真实易宝资金环境已验收。新渠道和全额分账保障默认关闭；必须完成平台收款商编角色、商家权限、手续费账户/全额补贴、回调格式、已分账退款归还顺序和实际账单格式的沙箱联调。归档 AES 密钥、商家材料 AES 密钥、YOP 私钥及官方证书需要外部配置。历史资金任务在关闭新支付后仍须继续。

本次自动化通过 Mockito、H2 事务、官方 SDK 协议及本地 HTTP 契约验证上述状态机与边界，不替代生产商户开户、密钥或真实资金联调；不对尚未执行的环境验收作通过声明。
